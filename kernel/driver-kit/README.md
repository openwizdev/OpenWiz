# Driver v1 test kit

Runs the five checks of [driver v1](../driver.v1.md) against one driver, on one throwaway ticket. **Platforms:** Linux and macOS, Python 3.9 or later, standard library only (it watches `/proc` on Linux, and `ps` on macOS). It never writes to GitHub: the agent the driver starts writes its own status note.

```sh
python3 -I kernel/driver-kit/kit.py --driver adapters/<host>/driver \
  --repo <owner>/<throwaway> --ticket <n> --harness <h> --model <m> [--skill build-ticket] [--effort medium] [--wait 900]
python3 -I kernel/driver-kit/test_kit.py     # the kit's own tests: the template passes, each planted driver fails
python3 -I kernel/driver-kit/test_hostkey.py # the key helper's own tests: every refusal, and the key never leaks
```

It prints one line per check, in the order version, start, wake, stop, token: `pass <check>: <what>` or `fail <check>: <why>`. Exit 0: all five pass. 1: a check failed. 2: the kit could not run; it says why on stderr, `kit.py: <why>`. The wake and stop checks run only after start passes. Once `start` has answered a run id, the kit always calls the driver's `stop` for that run before it goes on or exits, even when the start check failed; that stop is not the stop check.

## Effort

The `start` check also checks effort ([driver v1](../driver.v1.md#effort)). For a driver that declares it (effort in `can`, or an `Effort:` line), the line ends `; effort: <what>`. A failed effort part fails `start`. `--effort` is the word the kit sends (default `medium`). The kit reads the `Effort:` line in the `README.md` beside the driver, and the table of harness and flag (or `can't (<why>)`) right after it.

- **`can` lists `effort`:** the README needs an `Effort:` line naming the setting in backticks: `Effort: passed as <flag>`, or a table with one per harness. The kit's start carries `effort`, and that setting must reach the host:
  - **A flag** such as `` `--effort <level>` `` or `` `-c model_reasoning_effort=<level>` ``: the last token in the backticks holding a placeholder such as `<level>`, with the word put in, must be in the command line of a process the run started, right after the token before it in the backticks (`--effort medium`, not `--model medium`). A `NAME=<level>` setting also counts as that variable in the process's environment, unless the kit gave it unchanged. The kit watches every few milliseconds while `start` runs, and then the processes the token check watches, so a one-shot host command, such as `room-cli thread spawn --reasoning-level <level>`, counts.
  - **A request field** such as `` the `effort` field ``, for a key-host driver ([Key hosts](#key-hosts)): the kit first sends that start against its loopback fake host, then stops it, and a JSON request body the fake host received must hold that field with the word. The helper takes its request on stdin, so the command line doesn't count.
  - **Or it is refused:** with exactly the contract's refusal `next`, nothing left running and, for a key-host driver, no `POST` sent to the fake host; and the README says this harness can't (`Effort: the host can't set it`, or `can't` in the harness's row), or the word is not in the README's list (`, for low, medium and high` right after the setting, ending the sentence or followed by `,`, `.`, `;` or ` with`; a setting with no list claims every word). Then the kit runs the rest without `effort`. A refusal of a word the README lists fails, and so does a start taken for a harness the README says can't. A refusal with another `next` fails `start` with the driver's own error and `next`, with no second start.
- **`can` doesn't list `effort`:** the kit sends one extra start with `effort` first. It must be refused (D1), with nothing left running, and the README's `Effort:` line must say `Effort: the host can't set it (<why>)`.
- **No `Effort:` line, and `can` doesn't list `effort`:** the start still passes, and its line is unchanged. The kit prints the note on stderr: `note start: effort: not declared yet; required from EF14`. EF14 removes this.

## Key hosts

A host driven only through an API that takes the user's key is reached only through the key helper, [`hostkey.py`](hostkey.py) (driver v1 N4). The driver runs `python3 -I kernel/driver-kit/hostkey.py` with exactly `host`, `method` (`GET`, `POST` or `DELETE`), `path` and an optional `body` on stdin, and reads back exactly `status` and `body`, or a D3 error. The helper alone reads the key (16 to 4096 letters, digits or `._~+/=-`): from the host's variable in [`hosts.json`](hosts.json), or else its keychain entry through `/usr/bin/security` or `/usr/bin/secret-tool`. It sends the key only in an `Authorization: Bearer` header, over HTTPS with the system's TLS defaults (it clears `OPENSSL_*` and `SSL_*` variables first), to the registered origin. It refuses an unregistered host, an escaping path or a request that holds the key before any network call, follows no redirect, and never prints or stores the key. Adding a host is one reviewed entry in `hosts.json`. Under the kit's loopback override, `OPENWIZ_HOSTKEY_TEST_ORIGIN` (honoured only as `http://127.0.0.1:<port>`), the helper reads neither the host's variable nor the keychain: it asks the fake host for its test key.

When a driver's `README.md` names a registered host, the token check runs the key check. The driver runs without the host's variable, pointed at a loopback fake host. The fake gives its canary key only to a connection it traces to the key helper's own process. That process's executable must be the interpreter the kit itself runs on, its arguments exactly `-I` and the kit's `hostkey.py` (resolved from that process's own working folder), and it may carry no `LD_*` or `DYLD_*` variable. Missing evidence (an unreadable executable, folder or environment, or on macOS no environment row with the run's mark) refuses it. So the canary is never in the driver's environment, and a driver that shows it anywhere has handled the key itself. The check passes only when start, wake and stop each reached the fake host with the canary in the helper's `Authorization` header and nowhere else, and no other process asked for the key. No file of the driver's folder (symbolic links followed) may name the host's variable or call `security` or `secret-tool`, and neither may any script its processes run. Scripts are resolved from each process's working folder, and on macOS a path may hold spaces. In `README.md` only the variable and the keychain entry on one line together are exempt. A path argument that resolves to nothing, a process of the run that hides its details, or anything else the kit can't read, resolve or watch fails the check. Diagnostics never show a path or name that holds a credential or the canary. The fake host answers `200 {}`, or what the driver's `fixtures/kit-host.json` says: exactly `answers`, each exactly `method`, `path` (a pattern), `status` and `body`. The key check's nested `start` probe sends synthetic repository `example/site` rather than the outer `--repo`. A string value in `body` of the form `{{request.<field>}}` (or `{{request.<a.b>}}` for nested JSON objects, each segment matching `[A-Za-z_][A-Za-z0-9_-]*`) echoes that field from the request's JSON body, and `{{start.<field>}}` (`repository`, `ticket`, `skill`, `harness` or `model`) echoes that field from the nested probe's `start` input; any other `{{` or `}}` in `body` is refused as a malformed placeholder (exit 2), and a missing field or non-object request body answers `400`. Any README needs the helper and its registry, or the kit exits 2.

**Limits.** The operating system gives no launch identity: the kit recognises the helper by its executable, arguments, working folder and environment. Hostile code running as the same user can still imitate or attach to the helper, and so read a key the helper holds. The kit samples processes every 5 ms, so a child that starts and exits between two samples can go unseen; that sampling is diagnostics only, never the boundary. A module a driver imports without running it is not scanned. The driver's review covers all three.

## The throwaway ticket

Make a throwaway repository with a `docs/agents/fleet.md` whose `Record authors` row names the account your agents post as, and one open ticket in it. The kit reads the ticket's comments through a signed-in `gh` (GraphQL only), every 10 seconds, for up to `--wait` seconds per step. Close the ticket when you're done; the kit leaves it as it is.

`--tracker <file>` reads the ticket from a local file instead of GitHub, for the kit's own tests: a JSON object with exactly `record_authors` (logins) and `comments` (each exactly `id`, `author`, `updated_at` and `body`).

## What it doesn't see

It knows a credential by the status contract's credential rules or as the value of a secret in its own environment. It never shows a driver answer that holds one, in its text or once decoded: that answer fails with a fixed diagnostic.

It sees the processes a driver starts on this machine (each carries the kit's `OPENWIZ_KIT_RUN` mark in its environment), not what a remote host runs. The leftover scan reads an environment only for the run's own processes: descendants of the kit, processes in a process group or session where a marked process was already seen (never the kit's own group or session), and leftovers already recorded by pid and start time. On macOS a pid is not kept without a start time, and a group or session is forgotten once no listed process is in it. It does not read an unrelated process's environment. A driver that clears its children's environment hides them from the token and stop checks: its review must check that by reading its code.

On macOS, with no `/proc`, the kit lists processes with `ps -A` (pid, parent, group, session, state and command) and reads an environment with `ps -E` only for a process in that scope, never for every process. macOS prints `sess` as a session pointer, not the id `getsid` returns, so the kit's own session is the pointer on its own `ps` row. Where `ps` shows a process's environment, the mark finds it as on Linux. Where it shows none, the kit finds the run's processes by process group instead: a process belongs to the run when it is in a group where the kit has seen a marked process, never the kit's own group. On macOS a process's environment is what `ps -E` prints after its command line. The token check drops each variable the kit gave the driver unchanged, then splits the rest only where a new `NAME=` begins, so a value with spaces stays whole. First the kit checks that `ps -E` shows the environment of a process it starts itself. Where it doesn't, stop and token fail, because the kit can't tell which processes the driver started: `ps shows no process's environment here, so the kit cannot tell which processes the driver started`. Seeing the probe is not enough: stop and token pass only once `ps -E` has shown at least one of the run's own processes, carrying the mark. Where it never has, both fail as unverified, whatever the probe showed: `ps -E never showed a process of this run, so the kit cannot tell which processes the driver started`. So on macOS, a driver whose processes all run on another machine cannot pass stop and token here.

## Fixtures

- `fixtures/no-proc/`: runs Python as on macOS, on Linux: no `/proc`, no `prctl` and no pidfd, `sys.platform` `darwin`, and a `ps` that takes macOS's `-E` (with `NO_PROC_HIDE_ENV` set, it shows no environment at all; with `NO_PROC_PROBE_ONLY` set, only the kit's own probe's, and only in the kit's own listing: a caller with `OPENWIZ_KIT_RUN` set, as the driver is, keeps its own view). The drivers' and the kit's tests put it first on `PATH` to run the macOS path (#2010).
- `fixtures/fake-harness`: a synthetic harness. It posts one builder note into the tracker named by `KIT_TRACKER`, edits it when woken, then waits to be stopped. With `FAKE_ARGS` set, it appends its arguments to that file, one JSON list per turn.
- `fixtures/base/`: the kit's fixed driver, a copy of the template from before it declared effort, so the fixtures never follow the live template; with no `Effort:` line, it is the undeclared case. `test_kit.py` checks the live template in whichever form it declares.
- `fixtures/effort/`: the fixed driver with `effort` in `can`, passing it to the harness as `--effort` for the words its README lists, and refusing any other word with the refusal text. `fixtures/effort-refused/` refuses it for `fake-harness` with the refusal text, as its README's table says; `fixtures/effort-cant/` is the fixed driver with `Effort: the host can't set it`; `fixtures/effort-one-shot/` gives it only to a one-shot host command during `start`; `fixtures/effort-key-host/` is the key-host fixture, with effort in `can`, sending it in its start request. `fixtures/start-child/<form>/` runs a short-lived child holding a credential on its command line during the start that matters.
- `fixtures/planted/<name>`: the fixed driver with one planted break each; the single-file ones share `planted/README.md`, which says the host can't set effort. `test_kit.py` names the exact lines each must print. The effort ones: `effort-dropped` lists effort but never passes it, `effort-word-elsewhere` drops it and puts the same word in another option, `effort-wrong-next` refuses it with another `next`, `effort-refuses-listed` refuses a word its README lists, `effort-cant-harness-taken` takes it for a harness its README says can't, `effort-no-readme-line` passes it with no `Effort:` line, `effort-no-readme` has no README at all, `effort-taken-without-can` takes it without listing it, `effort-dropped-key-host` passes it to the harness but drops it from its start request, and `effort-key-host-starts-then-refuses` sends its start request to the host and then refuses.
- `evidence/`: the red run and the green run; `red-1586.txt`, `red-1586-r1.txt` and `green-1586.txt` are those of the credential fixes. `red-2039.txt` and `green-2039.txt` are those of the run-seen rule on macOS. `red-2379-*.txt` and `green-2379.txt` are those of the key helper and the key check; `red-2379-review-*.txt` and `green-2379-review.txt` are those of its review round. `red-2562.txt` and `green-2562.txt` are those of the effort check; `red-2562-r1-r4.txt` and `green-2562-r1-r4.txt` are those of its review round, `red-2562-r10-r13.txt` and `green-2562-r10-r13.txt` those of the refusal-retry round, and `red-2562-r10-delete-retry.txt` and `green-2562-r10-delete-retry.txt` those of the retry-deletion round.
