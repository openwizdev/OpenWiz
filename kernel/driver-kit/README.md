# Driver v1 test kit

Runs the five checks of [driver v1](../driver.v1.md) against one driver, on one throwaway ticket. **Platforms:** Linux and macOS, Python 3.9 or later, standard library only (it watches `/proc` on Linux, and `ps` on macOS). It never writes to GitHub: the agent the driver starts writes its own status note.

```sh
python3 -I kernel/driver-kit/kit.py --driver adapters/<host>/driver \
  --repo <owner>/<throwaway> --ticket <n> --harness <h> --model <m> [--skill build-ticket] [--wait 900]
python3 -I kernel/driver-kit/test_kit.py     # the kit's own tests: the template passes, each planted driver fails
python3 -I kernel/driver-kit/test_hostkey.py # the key helper's own tests: every refusal, and the key never leaks
```

It prints one line per check, in the order version, start, wake, stop, token: `pass <check>: <what>` or `fail <check>: <why>`. Exit 0: all five pass. 1: a check failed. 2: the kit could not run; it says why on stderr, `kit.py: <why>`. Wake and stop run only after start passes.

## Key hosts

A host driven only through an API that takes the user's key is reached only through the key helper, [`hostkey.py`](hostkey.py) (driver v1 N4). The driver runs `python3 -I kernel/driver-kit/hostkey.py` with exactly `host`, `method` (`GET`, `POST` or `DELETE`), `path` and an optional `body` on stdin, and reads back exactly `status` and `body`, or a D3 error. The helper alone reads the key (16 to 4096 letters, digits or `._~+/=-`): from the host's variable in [`hosts.json`](hosts.json), or else its keychain entry through `/usr/bin/security` or `/usr/bin/secret-tool`. It sends the key only in an `Authorization: Bearer` header, over HTTPS with the system's TLS defaults (it clears `OPENSSL_*` and `SSL_*` variables first), to the registered origin. It refuses an unregistered host, an escaping path or a request that holds the key before any network call, follows no redirect, and never prints or stores the key. Adding a host is one reviewed entry in `hosts.json`. Under the kit's loopback override, `OPENWIZ_HOSTKEY_TEST_ORIGIN` (honoured only as `http://127.0.0.1:<port>`), the helper reads neither the host's variable nor the keychain: it asks the fake host for its test key.

When a driver's `README.md` names a registered host, the token check runs the key check. The driver runs without the host's variable, pointed at a loopback fake host. The fake gives its canary key only to a connection it traces to the key helper's own process. That process's executable must be the interpreter the kit itself runs on, its arguments exactly `-I` and the kit's `hostkey.py` (resolved from that process's own working folder), and it may carry no `LD_*` or `DYLD_*` variable. Missing evidence (an unreadable executable, folder or environment, or on macOS no environment row with the run's mark) refuses it. So the canary is never in the driver's environment, and a driver that shows it anywhere has handled the key itself. The check passes only when start, wake and stop each reached the fake host with the canary in the helper's `Authorization` header and nowhere else, and no other process asked for the key. No file of the driver's folder (symbolic links followed) may name the host's variable or call `security` or `secret-tool`, and neither may any script its processes run. Scripts are resolved from each process's working folder, and on macOS a path may hold spaces. In `README.md` only the variable and the keychain entry on one line together are exempt. A path argument that resolves to nothing, a process of the run that hides its details, or anything else the kit can't read, resolve or watch fails the check. Diagnostics never show a path or name that holds a credential or the canary. The fake host answers `200 {}`, or what the driver's `fixtures/kit-host.json` says: exactly `answers`, each exactly `method`, `path` (a pattern), `status` and `body`. Any README needs the helper and its registry, or the kit exits 2.

**Limits.** The operating system gives no launch identity: the kit recognises the helper by its executable, arguments, working folder and environment. Hostile code running as the same user can still imitate or attach to the helper, and so read a key the helper holds. The kit samples processes every 5 ms, so a child that starts and exits between two samples can go unseen; that sampling is diagnostics only, never the boundary. A module a driver imports without running it is not scanned. The driver's review covers all three.

## The throwaway ticket

Make a throwaway repository with a `docs/agents/fleet.md` whose `Record authors` row names the account your agents post as, and one open ticket in it. The kit reads the ticket's comments through a signed-in `gh` (GraphQL only), every 10 seconds, for up to `--wait` seconds per step. Close the ticket when you're done; the kit leaves it as it is.

`--tracker <file>` reads the ticket from a local file instead of GitHub, for the kit's own tests: a JSON object with exactly `record_authors` (logins) and `comments` (each exactly `id`, `author`, `updated_at` and `body`).

## What it doesn't see

It knows a credential by the status contract's credential rules or as the value of a secret in its own environment. It never shows a driver answer that holds one, in its text or once decoded: that answer fails with a fixed diagnostic.

It sees the processes a driver starts on this machine (each carries the kit's `OPENWIZ_KIT_RUN` mark in its environment), not what a remote host runs. A driver that clears its children's environment hides them from the token and stop checks: its review must check that by reading its code.

On macOS, with no `/proc`, the kit lists processes with `ps -A`, and reads each one's environment with `ps -E`. Where `ps` shows a process's environment, the mark finds it as on Linux. Where it shows none, the kit finds the run's processes by process group instead: a process belongs to the run when it is in a group where the kit has seen a marked process, never the kit's own group. On macOS a process's environment is what `ps -E` prints after its command line. The token check drops each variable the kit gave the driver unchanged, then splits the rest only where a new `NAME=` begins, so a value with spaces stays whole. First the kit checks that `ps -E` shows the environment of a process it starts itself. Where it doesn't, stop and token fail, because the kit can't tell which processes the driver started: `ps shows no process's environment here, so the kit cannot tell which processes the driver started`. Seeing the probe is not enough: stop and token pass only once `ps -E` has shown at least one of the run's own processes, carrying the mark. Where it never has, both fail as unverified, whatever the probe showed: `ps -E never showed a process of this run, so the kit cannot tell which processes the driver started`. So on macOS, a driver whose processes all run on another machine cannot pass stop and token here.

## Fixtures

- `fixtures/no-proc/`: runs Python as on macOS, on Linux: no `/proc`, no `prctl` and no pidfd, `sys.platform` `darwin`, and a `ps` that takes macOS's `-E` (with `NO_PROC_HIDE_ENV` set, it shows no environment at all; with `NO_PROC_PROBE_ONLY` set, only the kit's own probe's). The drivers' and the kit's tests put it first on `PATH` to run the macOS path (#2010).
- `fixtures/fake-harness`: a synthetic harness. It posts one builder note into the tracker named by `KIT_TRACKER`, edits it when woken, then waits to be stopped.
- `fixtures/planted/<name>`: the template with one planted break each. `test_kit.py` names the exact lines each must print.
- `fixtures/key-host/`: a fake key-host driver, the template sending each start, wake and stop to host `devin` through the helper. `fixtures/planted/key-*/` are it with one key break each: it reads the key itself (in the driver, in a `test_*` file it imports, or in a script it runs, `fixtures/runtime-reader`), names the variable in its README (or twice on the login line), keeps it behind a symbolic link or in a script it runs by a relative or a credential-shaped path, passes the key in an argument, in another variable, in a variable's name or in a request body, prints it, sends it to the host itself, impersonates the helper (a Perl process with the helper's arguments), asks for an unregistered host or for a path with a host in it, calls the keychain tool, names a key host under a local login line, or meets a fake host whose `fixtures/kit-host.json` refuses start. `fixtures/key-host-dumps-env/` records its environment, to show the canary never reaches the driver. `test_kit.py` also runs it against a fake host that answers a redirect: start fails, and the redirect's target gets no request.
- `evidence/`: the red run and the green run; `red-1586.txt`, `red-1586-r1.txt` and `green-1586.txt` are those of the credential fixes. `red-2039.txt` and `green-2039.txt` are those of the run-seen rule on macOS. `red-2379-*.txt` and `green-2379.txt` are those of the key helper and the key check; `red-2379-review-*.txt` and `green-2379-review.txt` are those of its review round.
