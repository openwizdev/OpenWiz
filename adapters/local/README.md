# The local driver

Login: stays on your machine

The default host: a [driver v1](../../kernel/driver.v1.md) that runs builders on the machine it runs on, your computer or a VPS, with the harnesses you have already signed into. One Python file, standard library only. **Platforms:** Linux and macOS, Python 3.9 or later (it finds a run's processes through `/proc` on Linux, and through each turn's process group, `ps`'s process table and `lsof`'s list of processes writing to the run's log on macOS, never another process's environment). On macOS, a process that leaves its turn's group, closes or redirects its output (as a daemon does), and is orphaned before the supervisor's next look is out of reach of `stop`. If `lsof` can't run there, or fails other than by finding nothing, macOS uses only the turn groups and the processes the supervisors recorded: a detached worker they never recorded can survive `stop`, even while it holds the log open, and `stop` says on stderr that it could not check the run's output file.

```sh
echo '{"repository":"example/site","ticket":7,"skill":"build-ticket","harness":"claude","model":"claude-opus-5-5"}' \
  | adapters/local/driver start             # {"run": "run-0123456789ab"}
echo '{"run":"run-0123456789ab"}' | adapters/local/driver wake
echo '{"run":"run-0123456789ab"}' | adapters/local/driver stop
adapters/local/driver version               # {"driver": "local", ..., "can": [..., "many-at-once"]}
```

- **Harnesses:** `claude` runs `claude -p <prompt> --model <model> --permission-mode <mode>`; `codex` runs `codex exec --model <model> --sandbox <mode> <prompt>`. Each is found on `PATH` when the run starts. A harness that isn't installed, or isn't one of these, is a JSON error whose `next` says what to do.
- **Harness rows:** any other harness is a row, `harnesses/<harness>/row.json`, under the [harness-row contract](harness-row.md): its program, its start and wake command lines, how it knows its session id, its permission modes, its effort and where its login lives. `start` reads the row only for the harness it names; a missing or broken row is a JSON error that names the row file and starts nothing, and the "use one of" error lists the built-ins plus the row folders. A row's turns get its `env` and only the approved mode's arguments; stop (after the row's own `stop` command, when it has one), the approvals, the first-turn watch and the credential check are the same as for the built-ins. A start with an effort its row can't take is refused and starts nothing, never falling back to a default. Each row adds one folder and touches no shared file.
- **Permission mode:** the owner chooses it once, during setup, for each repository and harness, and saves it in two places. On this machine, outside any repository, it goes in `$OPENWIZ_LOCAL_STATE/approvals.json` (owner-only, mode 600), as `{"<owner>/<name>": {"claude": "<mode>"}}`. In the repository's `docs/agents/fleet.md`, it goes in one row: `| Harness permission mode | `<mode>` |`, or, since Claude Code and Codex take different values, in one row per harness: `| Harness permission mode (claude) | `<mode>` |` and `| Harness permission mode (codex) | `<mode>` |`. Use a `claude --permission-mode` value for claude and a `codex --sandbox` value for codex. `start` checks this machine's approval for the harness it starts before cloning, and the clone's row for that harness (its own row, or else the single row) must match it exactly. A file with both the single row and that harness's own row is refused; once a file has any per-harness row and no single row, a harness without its own row is refused, and both errors name the harness. Once a file has a per-harness row, every row's first cell is read with its spaces trimmed and collapsed, as Markdown tables allow, so an aligned copy of a row still counts as that row. Only the approved value is passed, unchanged, as that harness's own option. The driver never uses a mode it read only from a repository, and never chooses, adds or widens one. With no approval on this machine, an approvals file others can change, or a missing or different row, `start` refuses before anything runs, and its `next` names the setup step that fixes it. Without a mode, a stock harness in `-p`/`exec` refuses every tool and the builder can do nothing.
- **No credential in a start field:** `start` refuses a field whose value has a credential's shape, by the driver kit's own check (`kernel/driver-kit/kit.py`), before it saves or runs anything, and its error names the field, never the value.
- **Logins:** none. The driver adds no login or token. Each turn, and the clone, inherit the environment of whoever runs the driver (the turn also gets `OPENWIZ_RUN`). A row's harness also gets the row's fixed `env` and the requested effort's setting, which pass the kit's credential check; the turn's supervisor keeps the driver's environment unchanged. The harness's and `gh`'s own sign-ins decide what they may reach.
- **Workspaces:** each run gets its own fresh clone of the request's repository (`gh repo clone`, the person's own signed-in GitHub CLI), in `$OPENWIZ_LOCAL_STATE/work/<run>`. Every turn of that run works there, and two runs never share a checkout. A workspace stays after `stop`, in case it holds unpushed work; delete it when you are done.
- **First turn:** `start` watches the first turn for `$OPENWIZ_LOCAL_SETTLE` seconds (default 30) before it answers. A first turn that has already ended with a non-zero exit, or with a log line that opens, after at most two short labels such as `Error:`, with a refusal or sign-in diagnostic (such as a denied tool permission, an expired login, or a bare `Unauthorized` status: a harness refusing its tools can still exit 0), fails `start`; a clean turn's summary that only mentions permissions, logins or unauthorized requests does not. A first turn that ended cleanly, exit 0, simply finished, and `start` answers its run.
- **Errors never repeat raw output:** the clone's and every turn's output goes only to the run's owner-only log (`$OPENWIZ_LOCAL_STATE/<run>.log`). A failed clone or first turn answers a fixed reason (not signed in, refused a tool, failed, could not clone), its exit code, and that log's path.
- **Runs:** `start` saves the run, then runs its first turn. A run whose first turn began but couldn't be saved is ended, and its error says the outcome is unknown and what to check; it never says retry. `wake` runs another turn on the same ticket, in which the agent edits its own status note. While the run's last turn is still running, `wake` answers `woke: true` and starts no second turn, so one ticket never has two agents. On Linux, `stop` ends every process the run's turns started, whatever their session or environment: a polite signal, then a kill after 10 seconds. Each turn runs under a small supervisor (`driver --turn`) that keeps every process it starts (a Linux subreaper), so a worker in its own session or with a clean environment is still stopped. On macOS, `stop` ends every process it can find, within the gap and the `lsof` fallback above. A wake and a stop on one run take turns under its lock. Several runs at once are independent.
- **State:** each run's request, its workspace and each turn's output log, owner-only, in `$OPENWIZ_LOCAL_STATE` (default `~/.local/state/openwiz-local`).
- **Usage limits and overload:** when a turn ends non-zero with a usage-limit or overload message in the last lines of its log (built in for `claude` and `codex`, or via a row's optional `limit` pattern), its supervisor waits out the window (`reset + 15 s + up to 30 s` random jitter, or `60 s` then `120 s` then stop for overload with no reset time) and resumes once with the normal wake prompt on the same harness and model. Resets more than 6 hours away are not waited for; during a wait (or before a >6-hour reset), `wake` refuses under D3 naming the limit and reset time, and `start`'s first-turn check reports a limit the same way.
- **On a VPS:** sign in to the harness and to `gh` there, and run the driver there, for example over `ssh`.
- **Linux process environment:** on Linux, each turn gets an owner-only shell helper (`BASH_ENV`, plus `CLAUDE_ENV_FILE` for `claude`, sourcing any existing file) that raises the shell's `/proc/self/oom_score_adj` to 500 while the harness keeps its default; when the driver's cgroup sets a CPU quota (`cpu.max` or `cpu.cfs_quota_us`/`cpu.cfs_period_us`), the turn also gets `OMP_NUM_THREADS`, `PYTHON_CPU_COUNT` and `CARGO_BUILD_JOBS` set to the ceiling of quota over period unless already set. Nothing changes on macOS or when no quota is set.

`schema.json` is byte for byte the kit's `kernel/driver-kit/schema.json`.

## Tests

```sh
python3 -I adapters/local/test_driver.py    # the kit's five checks and every rule above, with a synthetic claude, codex and gh
python3 -I adapters/local/test_harnesses.py # the kit check for harness rows: its planted rows, then every row in harnesses/
```

The real-host run is the kit's, on a throwaway ticket, with a real signed-in harness and `gh`. The throwaway repository's `docs/agents/fleet.md` needs its `Record authors` row and its `Harness permission mode` row, and this machine's `approvals.json` the same mode for that repository and harness:

```sh
python3 -I kernel/driver-kit/kit.py --driver adapters/local/driver --repo <owner>/<throwaway> --ticket <n> \
  --harness claude --model <model>
```
