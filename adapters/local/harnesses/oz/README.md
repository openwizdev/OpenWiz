# Warp's local agent, `oz` (local runs)

Login: Warp's own sign-in on this machine: `oz login` (cached by oz), an existing Warp app sign-in, or WARP_API_KEY that you set yourself; the row never reads or passes a login and never uses --api-key

**A wake needs Warp's "Store AI conversations in the cloud" setting turned on** (Warp app: **Settings** > **Privacy**). With it off, Warp keeps conversations only on this device, and `oz agent run --conversation` continues an existing *cloud* conversation, so the wake has nothing to resume. See [Cloud-synced conversations](https://docs.warp.dev/agents/local-agents/cloud-conversations/), "Enabling cloud conversations". Enterprise admins can turn this sync off for the whole team; then a wake can't work.

A harness row for the [local driver](../../README.md), in the shape of the [harness-row contract](../../harness-row.md). It runs [Warp's Oz CLI](https://docs.warp.dev/agents/cli/oz-cli/) as a local agent on this machine (`oz agent run`); cloud runs (`oz agent run-cloud`) are out of scope.

Effort: none

- **Start:** `oz agent run --output-format json --model <model> <mode's arguments> --prompt <prompt>`.
- **Wake (same run):** `oz agent run --conversation <session> --model <model> <mode's arguments> --prompt <prompt>`. `--model` is passed again, as Warp allows on every `agent run`.
- **Session:** reported. oz picks the conversation id; the row reads it from the `conversation_started` line of the JSON output (see [the census check](#the-census-check-the-conversation-id)).
- **Stop:** the driver ends the run's process tree. oz runs the agent's commands in a shell on its own pseudo-terminal, so the row declares that shell as its background process, and the runner proves stop ends it.
- **Effort:** none: a start that carries an effort is refused and starts nothing (see [the effort fact](#the-effort-fact)).
- **Permission mode:** `default-profile` passes nothing, so oz uses its default agent profile, which Warp documents as "broadly permissive" for CLI use (read and write files, run commands with a default denylist). A profile is chosen with `--profile <ID>`, but profile ids are your own, so the row can't fix one. Approve `default-profile` for `oz` as for a built-in harness.
- **Login:** the driver never reads, sets or passes a login, and never passes `--api-key` (oz would save it with the run's arguments). oz finds its own: a cached `oz login`, the Warp app's sign-in on this host, or `WARP_API_KEY` from your environment ([Oz CLI](https://docs.warp.dev/agents/cli/oz-cli/), "Logging in").

## The census check: the conversation id

**Yes: the JSON output prints the conversation id, under the key `conversation_id` of a `conversation_started` system line**, and it is the id `--conversation` takes:

- [`app/src/ai/agent_sdk/driver/output.rs`](https://github.com/warpdotdev/warp/blob/f8223cef2d167a5858bf233df8a1fb6f74537fa5/app/src/ai/agent_sdk/driver/output.rs), module `json`: `JsonMessage` is tagged by `type`, its `System` variant by `event_type`, and `ConversationStarted { conversation_id }` is written with `serde_json::to_writer` as one compact line: `{"type":"system","event_type":"conversation_started","conversation_id":"<id>"}`.
- [`app/src/ai/agent_sdk/driver.rs`](https://github.com/warpdotdev/warp/blob/f8223cef2d167a5858bf233df8a1fb6f74537fa5/app/src/ai/agent_sdk/driver.rs): with `--output-format json` or `ndjson`, the driver writes that line once, as soon as the server has given the conversation its token (`server_conversation_token`). In `pretty` or `text` it prints `New conversation started with debug ID: <id>` instead.
- [`app/src/ai/agent_sdk/mod.rs`](https://github.com/warpdotdev/warp/blob/f8223cef2d167a5858bf233df8a1fb6f74537fa5/app/src/ai/agent_sdk/mod.rs): `--conversation` is wrapped as a `ServerConversationToken` to load the conversation it resumes, the same server token the line reports.

**Why a pattern, not a JSON key path.** At `f8223cef`, a `hook_notice` line also has a `conversation_id` key, and it is `null` until the server assigns the token ([`driver/hooks.rs`](https://github.com/warpdotdev/warp/blob/f8223cef2d167a5858bf233df8a1fb6f74537fa5/app/src/ai/agent_sdk/driver/hooks.rs), `write_notice`; the June tag has no `driver/hooks.rs`). The contract's `{"json": ["conversation_id"]}` reads the first line with that key and stops there, so a hook notice printed first would leave the run with no session id. The row's `session` is the pattern `"event_type":"conversation_started","conversation_id":"(...)"`, which only the `conversation_started` line matches. `test_row.py` proves the id is read past such a null `hook_notice`.

The check doesn't go against the row: the start prints the id, and the wake passes it to `--conversation`, as long as cloud conversations are on (the first section). The live check (#2560) records a real wake reaching the same conversation.

## The effort fact

oz can't set effort apart from the model, so the row declares effort none, as `row.json` says: `"effort": "none: oz agent run has no effort flag or setting; Warp puts the reasoning level in the model id (warpdotdev/warp crates/warp_cli at f8223cef, docs.warp.dev/agents/inference/model-choice)"`.

1. `RunAgentArgs` and the global options in `crates/warp_cli` (at `f8223cef` and at the June release tag) have no effort, reasoning or thinking flag, and no setting for one.
2. [Model choice](https://docs.warp.dev/agents/inference/model-choice/): the reasoning level is part of the model id: for OpenAI models "The `low`, `medium`, `high`, `xhigh`, and `max` suffixes select increasing reasoning levels", and for Anthropic models "Suffixes select effort level", with ids such as `claude-5-2-fable-high`. The levels differ per model (some families stop at `xhigh`, some have only `-thinking`), so no fixed effort map holds for every model.

So pick the level through the model id in your Models table, and leave the effort empty for `oz`. A start that carries an effort is a D3 error that starts nothing, with this `next`: "this host can't set effort: remove the effort for this harness in your Models table or Roster to run it at the host's default".

## Not installed, not signed in

- `oz` not on `PATH`: the driver's D3 error `harness oz is not installed here`, whose `next` says to install oz and sign in to it yourself. Warp's [install steps](https://docs.warp.dev/agents/cli/oz-cli/#installing-the-cli): with the Warp app, or the standalone `oz` package (`brew install --cask oz`, or `oz-stable` through apt, yum or pacman).
- Not signed in: oz refuses with one of these lines, and the row's four `signed_out` patterns match all of them, so `start` fails with the driver's D3 error `the harness is not signed in`, whose `next` names `oz login`:
  - signed out, at `f8223cef`: ``You are not logged in. Please log in again with `oz login` to continue.`` (`authenticate_then_execute` in [`app/src/ai/agent_sdk/mod.rs`](https://github.com/warpdotdev/warp/blob/f8223cef2d167a5858bf233df8a1fb6f74537fa5/app/src/ai/agent_sdk/mod.rs));
  - a saved login the server no longer accepts, at `f8223cef`: ``Your credentials are invalid. Please log in again with `oz login` to continue. If it appears that you are already logged in, log out and log in again.`` (`AuthManagerEvent::NeedsReauth`, same file), and at the June tag ``Your credentials are invalid. Please log in again with `oz login`.``;
  - signed out, at the June tag: ``You are not logged in - please log in with `oz login` to continue.`` (`launch_command` in [`app/src/ai/agent_sdk/mod.rs`](https://github.com/warpdotdev/warp/blob/v0.2026.06.03.09.49.stable_00/app/src/ai/agent_sdk/mod.rs));
  - once a run has started: `Failed to authenticate with server - please log in via 'oz login', ...` (`AgentDriverError::NotLoggedIn` in `driver.rs`).

The platforms the row holds on are the ones its live check runs on.
