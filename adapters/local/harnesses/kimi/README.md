# Kimi Code CLI (`kimi`) harness row

Login: kimi's own login, saved by `kimi login` under ~/.kimi-code/credentials/ (or $KIMI_CODE_HOME/credentials/)

Effort: none

Live check: #3367

Platforms: Linux only (see Stop)

This row never reads, sets or stores a login or key: a turn uses whatever `kimi login` (or the TUI's `/login`) saved. `kimi login` is Kimi Code's OAuth device-code flow, and it writes its token to `credentials/` under `~/.kimi-code`, or under `KIMI_CODE_HOME` when that is set ([`kimi login`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/reference/kimi-command.md#kimi-login), [data locations](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/configuration/data-locations.md), [`packages/oauth/src/toolkit.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/oauth/src/toolkit.ts)). Not installed: the driver refuses before anything starts. Signed out: a `-p` turn checks its model's credential before the first model call (`ensureReady` in `runNativeTurn`, [`run-v2-print.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/v2/run-v2-print.ts)); with no `kimi login` token for the managed provider it throws `provider managed:kimi-code has no credential configured` ([`auth.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/agent-core-v2/src/app/auth/auth.ts), [`authService.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/agent-core-v2/src/app/auth/authService.ts)), which `main.ts` prints as `error: failed to run prompt: <message>` before exiting 1. The row's one `signed_out` pattern is that message, so `start` fails with `the harness is not signed in` and `next` names `kimi login`. It is the managed provider's line only: a third-party provider's missing key (`provider <name> has no credential configured`, or a missing key variable) and a model that resolves to no provider stay a plain `the harness failed`, because `kimi login` doesn't fix them; `test_row.py` checks both sides.

The turn commands, login and overload handling use Kimi Code CLI **2.7.2** (tag `@moonshot-ai/kimi-code@2.7.2`, commit `56145f8`): its docs, its source and the option table its `--help` prints. The tests run only the fake CLI.

## Commands

- **Start:** `kimi -p {prompt} --output-format stream-json -m {model} {mode}` in the run’s clone. In `stream-json` every stdout line is one JSON object, and the run ends with the meta line `{"role":"meta","type":"session.resume_hint","session_id":"session_<uuid>",...}` ([print guide](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/guides/print.md), `writeResumeHint` in [`apps/kimi-code/src/cli/prompt-render.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/prompt-render.ts)). So the session is `{"json": ["session_id"]}`, read from the run's log. The busy-session error line (`{"type":"error",...}`, exit 4) has no `session_id`.
- **Wake (same run):** `kimi -S {session} -p {prompt} {mode}`. A resumed `-p` run keeps the session's saved model when `-m` is absent, and must run in the directory the session was made in, which the driver's clone is (`applyModelOverride` and the directory check before `resumeById` in [`run-v2-print.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/v2/run-v2-print.ts#L354-L408), and [the resumed-model test](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/test/cli/v2-run-print.test.ts#L962-L992)).
- **Stop:** the driver ends the run's process tree. Kimi's background Bash tasks are the process a stop must reach: on Unix kimi spawns each with `detached: true` and piped stdin, stdout and stderr, so each leads its own session and process group while its output still goes back to kimi (`buildSpawnOptions` in [`hostProcessService.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/agent-core-v2/src/os/backends/node-local/hostProcessService.ts)). A turn that ends normally tries to stop them as its session closes (`quiesceSessionAgents` in `run-v2-print.ts`), but a stopped turn may never get there. On Linux the driver's stop ends them with the process tree, and the kit's runner checks that with the fake. On macOS the driver samples the tree, and a task in its own session can leave the turn's group before a look, so **the row claims Linux only** pending a live macOS stop with an active background Bash task. The row's `env` sets `KIMI_CODE_NO_AUTO_UPDATE=1`, which makes `runUpdatePreflight` return at once ([environment variables](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/configuration/env-vars.md)). The detached installer (`tryStartAutomaticBackgroundInstall` in [`apps/kimi-code/src/cli/update/preflight.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/update/preflight.ts)) can't start under `-p` anyway, because print mode runs the preflight with `isTTY: false` and both paths to it need an interactive terminal (`main.ts`); the switch still skips the passive update check and its background refresh. `kimi web` runs in the foreground only, and `-p` never starts it; the hidden `kimi server ensure-daemon` is run only by the local server's SSH bridge for a remote host ([`packages/kap-server/src/services/hosts/sshKapBridge.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/kap-server/src/services/hosts/sshKapBridge.ts)).
- **Modes:** one, `auto`, which adds nothing (the census check below).

## Model

`{model}` is one whole argument to `-m`. Use a key from `[models]` in `config.toml` or an alias synced by a configured provider, such as `kimi-code/kimi-for-coding`. The CLI checks the explicit alias during profile binding and rejects an unknown alias before starting the turn. The CLI’s own check covers the effective catalog, so the row needs no model precheck. [`kimi -m`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/reference/kimi-command.md), [model keys](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/configuration/config-files.md#models), [model selection](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/v2/run-v2-print.ts#L436-L445), [catalog lookup](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/agent-core-v2/src/llm-adapter/model/catalog-service.ts#L229-L239)

## The census check: which permission options does `-p` accept?

**None.** `-p` takes no permission option, and always runs under kimi's `auto` permission policy.

1. The [`kimi` command reference](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/reference/kimi-command.md#flag-conflict-rules), "Flag Conflict Rules": "`--prompt` cannot be used with `--yolo`, `--auto`, or `--plan` — non-interactive mode uses `auto` permission by default". Its option table lists no other permission flag; `--yes` and `--auto-approve` are hidden aliases for `--yolo`.
2. The source agrees: `validateOptions` in [`apps/kimi-code/src/cli/options.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/options.ts) throws `Cannot combine --prompt with --yolo.`, `... with --auto.` and `... with --plan.`, and folds `--yes` and `--auto-approve` into `yolo` first. The flags themselves are declared in [`apps/kimi-code/src/cli/commands.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/commands.ts), the table `--help` prints.
3. In `-p`, "no human approval is requested — regular tool calls are handled under the `auto` permission policy, while static deny rules remain in effect" (the command reference, "Non-Interactive Execution"; [print guide](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/guides/print.md#permissions-and-exit-codes): "no need to pass `--auto` or `--yolo`"). A resumed `-p` run is forced to `auto` too (`forceAuto` in `run-v2-print.ts`).

**Answer.** `modes` maps only `auto` to no arguments: it is the policy every `-p` turn runs under, and the owner's approval of `auto` names it. No `--yolo`, `--auto` or `--plan` is mapped, because each makes kimi exit 1 at startup. Narrowing it is the user's own kimi `deny` rules, which `-p` keeps. The fake exits 2 on each refused flag, and `test_row.py` proves it.

## Effort

The row keeps `none`. Kimi Code CLI 2.8.1 and the latest checked tag, `@moonshot-ai/kimi-code@2.9.0-canary.20261127130549-5304618`, expose no headless effort option or read-only check that reports the effective effort for the print turn. `KIMI_MODEL_THINKING_EFFORT` can be dropped when the provider does not use thinking traits or the effective thinking is off. The provider list exposes configured entries, and the public catalog lists model metadata. The print turn computes its effective thinking from the bound model, provider and local settings. [2.8.1 resolver](https://github.com/MoonshotAI/kimi-code/blob/62402f173c5a838a1c1f8fa263b637a22486fa39/packages/core/src/llm/thinking.ts#L104), [canary resolver](https://github.com/MoonshotAI/kimi-code/blob/53046183bddd15c2b0e96e98993e81b0c0764a6f/packages/core/src/llm/thinking.ts#L104), [canary profile](https://github.com/MoonshotAI/kimi-code/blob/53046183bddd15c2b0e96e98993e81b0c0764a6f/packages/agent-core-v2/src/agent/profile/profileService.ts#L667), [canary command reference](https://github.com/MoonshotAI/kimi-code/blob/53046183bddd15c2b0e96e98993e81b0c0764a6f/docs/en/reference/kimi-command.md)

When the driver accepts the `effort` request field, a start with any effort starts nothing and returns `this host can't set effort: remove the effort for this harness in your Models table or Roster to run it at the host's default`. The runner exercises the refusal below the request parser until #2471 enables the field.

## Usage limits

On a failed print turn, Kimi Code CLI 2.7.2 emits `error: failed to run prompt: provider.overloaded: llm request failed` for the upstream overload test case. The row matches the stable `provider.overloaded:` prefix with the CLI’s error wrapper. Kimi appends the provider’s message. The cited line has no reset timestamp, so the driver waits one minute before trying a wake once for an existing session. If the message includes a reset time in a format AD2 recognizes, the driver uses that time. A first turn that exits before reporting a session ID returns the limit refusal and asks the caller to start again. [Print failure](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/v2/run-v2-print.ts#L1034-L1047), [overload test](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/test/cli/v2-run-print.test.ts#L1010-L1033), [CLI error wrapper](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/startup-error.ts#L15-L26)

## Synthetic

`fake` is the only CLI here. Its `HELP` text restates the command lines it allows; it prints kimi's resume-hint line with a synthetic `fake-<hex>` id, and kimi's missing-login line when the runner asks for a signed-out turn. `FAKE_CLI_LIMIT=1` prints the upstream overload test line on stderr and exits 1. With `KIMI_CODE_NO_AUTO_UPDATE=1` a start turn leaves one background process shaped like a kimi Bash task (its own session and process group, piped stdio) on every platform, so it does not stand in for the shared fixture's macOS service, which stays in the turn's group; without the switch it hands its work to the runner's hub outside the run. `test_row.py` checks the fake's refusals and accepted lines, the `signed_out` pattern on both sides, and, where `/proc` exists, the background process's shape, with synthetic prompts and ids. `evidence/` holds the red and green runs.
