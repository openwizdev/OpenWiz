# Kimi Code CLI (`kimi`) harness row

Login: kimi's own login, saved by `kimi login` under ~/.kimi-code/credentials/ (or $KIMI_CODE_HOME/credentials/)

Effort: none

Live check: #2519

Platforms: Linux only, until the live check's stop ends a background Bash task on macOS (see Stop)

This row never reads, sets or stores a login or key: a turn uses whatever `kimi login` (or the TUI's `/login`) saved. `kimi login` is Kimi Code's OAuth device-code flow, and it writes its token to `credentials/` under `~/.kimi-code`, or under `KIMI_CODE_HOME` when that is set ([`kimi login`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/reference/kimi-command.md#kimi-login), [data locations](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/configuration/data-locations.md), [`packages/oauth/src/toolkit.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/oauth/src/toolkit.ts)). Not installed: the driver refuses before anything starts. Signed out: a `-p` turn checks its model's credential before the first model call (`ensureReady` in `runNativeTurn`, [`run-v2-print.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/v2/run-v2-print.ts)); with no `kimi login` token for the managed provider it throws `provider managed:kimi-code has no credential configured` ([`auth.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/agent-core-v2/src/app/auth/auth.ts), [`authService.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/agent-core-v2/src/app/auth/authService.ts)), which `main.ts` prints as `error: failed to run prompt: <message>` before exiting 1. The row's one `signed_out` pattern is that message, so `start` fails with `the harness is not signed in` and `next` names `kimi login`. It is the managed provider's line only: a third-party provider's missing key (`provider <name> has no credential configured`, or a missing key variable) and a model that resolves to no provider stay a plain `the harness failed`, because `kimi login` doesn't fix them; `test_row.py` checks both sides.

Every fact below is read from Kimi Code CLI **2.7.2** (tag `@moonshot-ai/kimi-code@2.7.2`, commit `56145f8`): its docs, its source and the option table its `--help` prints. Nothing was run: no sign-in, no model call, no real `kimi`.

## Commands

- **Start:** `kimi -p {prompt} --output-format stream-json -m {model} {mode}`. In `stream-json` every stdout line is one JSON object, and the run ends with the meta line `{"role":"meta","type":"session.resume_hint","session_id":"session_<uuid>",...}` ([print guide](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/guides/print.md), `writeResumeHint` in [`apps/kimi-code/src/cli/prompt-render.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/prompt-render.ts)). So the session is `{"json": ["session_id"]}`, read from the run's log. The busy-session error line (`{"type":"error",...}`, exit 4) has no `session_id`. `{model}` is a kimi model alias, such as `kimi-code/kimi-for-coding`.
- **Wake (same run):** `kimi -S {session} -p {prompt} {mode}`. A resumed `-p` run keeps the session's saved model when `-m` is absent, and must run in the directory the session was made in, which the driver's clone is (`applyModelOverride` and the directory check before `resumeById` in [`apps/kimi-code/src/cli/v2/run-v2-print.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/v2/run-v2-print.ts)).
- **Stop:** the driver ends the run's process tree. Kimi's background Bash tasks are the process a stop must reach: on Unix kimi spawns each with `detached: true` and piped stdin, stdout and stderr, so each leads its own session and process group while its output still goes back to kimi (`buildSpawnOptions` in [`hostProcessService.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/agent-core-v2/src/os/backends/node-local/hostProcessService.ts)). A turn that ends normally tries to stop them as its session closes (`quiesceSessionAgents` in `run-v2-print.ts`), but a stopped turn may never get there. On Linux the driver's stop ends them with the process tree, and the kit's runner checks that with the fake. On macOS the driver samples the tree, and a task in its own session can leave the turn's group before a look, so **the row claims Linux only** until its live check (#2519) stops a turn with an active background Bash task on macOS. The row's `env` sets `KIMI_CODE_NO_AUTO_UPDATE=1`, which makes `runUpdatePreflight` return at once ([environment variables](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/configuration/env-vars.md)). The detached installer (`tryStartAutomaticBackgroundInstall` in [`apps/kimi-code/src/cli/update/preflight.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/update/preflight.ts)) can't start under `-p` anyway, because print mode runs the preflight with `isTTY: false` and both paths to it need an interactive terminal (`main.ts`); the switch still skips the passive update check and its background refresh. `kimi web` runs in the foreground only, and `-p` never starts it; the hidden `kimi server ensure-daemon` is run only by the local server's SSH bridge for a remote host ([`packages/kap-server/src/services/hosts/sshKapBridge.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/kap-server/src/services/hosts/sshKapBridge.ts)).
- **Modes:** one, `auto`, which adds nothing (the census check below).

## The census check: which permission options does `-p` accept?

**None.** `-p` takes no permission option, and always runs under kimi's `auto` permission policy.

1. The [`kimi` command reference](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/reference/kimi-command.md#flag-conflict-rules), "Flag Conflict Rules": "`--prompt` cannot be used with `--yolo`, `--auto`, or `--plan` — non-interactive mode uses `auto` permission by default". Its option table lists no other permission flag; `--yes` and `--auto-approve` are hidden aliases for `--yolo`.
2. The source agrees: `validateOptions` in [`apps/kimi-code/src/cli/options.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/options.ts) throws `Cannot combine --prompt with --yolo.`, `... with --auto.` and `... with --plan.`, and folds `--yes` and `--auto-approve` into `yolo` first. The flags themselves are declared in [`apps/kimi-code/src/cli/commands.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/apps/kimi-code/src/cli/commands.ts), the table `--help` prints.
3. In `-p`, "no human approval is requested — regular tool calls are handled under the `auto` permission policy, while static deny rules remain in effect" (the command reference, "Non-Interactive Execution"; [print guide](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/guides/print.md#permissions-and-exit-codes): "no need to pass `--auto` or `--yolo`"). A resumed `-p` run is forced to `auto` too (`forceAuto` in `run-v2-print.ts`).

**Answer.** `modes` maps only `auto` to no arguments: it is the policy every `-p` turn runs under, and the owner's approval of `auto` names it. No `--yolo`, `--auto` or `--plan` is mapped, because each makes kimi exit 1 at startup. Narrowing it is the user's own kimi `deny` rules, which `-p` keeps. The fake exits 2 on each refused flag, and `test_row.py` proves it.

## Effort

The row takes the `none` form: `"effort": "none: ..."`. Once the local driver's `effort` start field is on (driver v1's effort change, EF4 of #2471, as harness-row §4 describes), any start that carries an effort is a D3 refusal that starts nothing, with `next` exactly `this host can't set effort: remove the effort for this harness in your Models table or Roster to run it at the host's default`; the runner proves that message below the request parser today. Until then the driver takes no `effort` field at all, so a start that carries one is refused by the request check (`the input needs exactly repository, ticket, skill, harness, model`) and starts nothing either.

- **No flag:** the option table in `commands.ts` and the command reference have no effort, thinking or reasoning flag.
- **The environment setting is ignored for some models:** `KIMI_MODEL_THINKING_EFFORT` sets `thinking.forcedEffort` (`thinkingEnvBindings` in [`packages/agent-core-v2/src/app/kosongConfig/configSection.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/agent-core-v2/src/app/kosongConfig/configSection.ts)), but `resolveForcedThinkingEffort` in [`packages/core/src/llm/thinking.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/core/src/llm/thinking.ts) returns nothing unless the model's provider is "thinking-driven", and only the `kimi` provider is ([`packages/agent-core-v2/src/llm-adapter/provider/provider-definition.ts`](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/packages/agent-core-v2/src/llm-adapter/provider/provider-definition.ts)); it is dropped too when thinking is off. The docs say the same: "`kimi` provider only" ([environment variables](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/configuration/env-vars.md)). A kimi alias can name an `anthropic`, `openai` or `google-genai` provider, where the setting does nothing.
- **The config key falls back:** `[thinking] effort` "falls back to the model default when not in its supported list" ([config files](https://github.com/MoonshotAI/kimi-code/blob/56145f849caa305d42acd09b67fb65d11146f887/docs/en/configuration/config-files.md#thinking); `normalizeThinkingEffortForModel` in `thinking.ts`), and the driver can't write the user's `config.toml` anyway.

A silent drop or fallback is what the harness-row contract forbids, so the row declares `none` rather than claim an effort kimi may ignore.

## Synthetic

`fake` is the only CLI here. Its `HELP` text restates the command lines it allows; it prints kimi's resume-hint line with a synthetic `fake-<hex>` id, and kimi's missing-login line when the runner asks for a signed-out turn. With `KIMI_CODE_NO_AUTO_UPDATE=1` a start turn leaves one background process shaped like a kimi Bash task (its own session and process group, piped stdio) on every platform, so it does not stand in for the shared fixture's macOS service, which stays in the turn's group; without the switch it hands its work to the runner's hub outside the run. `test_row.py` checks the fake's refusals and accepted lines, the `signed_out` pattern on both sides, and, where `/proc` exists, the background process's shape, with synthetic prompts and ids. `evidence/` holds the red and green runs.
