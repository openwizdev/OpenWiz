# Fly Sprites driver
Login: held by Fly.io

Effort: passed as each harness's own flag, for the harnesses and levels in the table below; any other harness or level is refused before anything is created, and a `start` with no effort runs at the harness's default

| Harness | Effort |
| --- | --- |
| `claude` | `--effort <level>`, for low, medium, high, xhigh and max |
| `codex` | `-c model_reasoning_effort=<level>`, for low, medium, high, xhigh, max and ultra |
| any other harness | can't (this driver runs only `claude` and `codex`, each through its own connector) |

**Billing: Claude Code runs on an Anthropic API key, not a Claude subscription.** Claude Code goes through Fly's Anthropic connector, which holds an Anthropic API key and bills your Anthropic account for every request; a Claude Pro or Max subscription can't be used. Codex through this driver uses an OpenAI API key connector, which bills your OpenAI project; a ChatGPT plan through Fly's [Codex connector](https://fly.io/sprites/ecosystem/#connectors/codex) isn't supported yet. Source: Fly's [connector catalog](https://fly.io/sprites/ecosystem/) (its Anthropic, OpenAI and Codex entries) and [connectors](https://docs.fly.io/sprites/concepts/connectors) docs.

A [driver v1](../../kernel/driver.v1.md) that runs each builder in its own [Fly Sprite](https://docs.fly.io/sprites), through your own signed-in `sprite` CLI. One Python file, standard library only, built from [`adapters/template/`](../template/) with the [boat driver](../boat/README.md) as prior art. **Platforms:** Linux and macOS, Python 3.9 or later (on Linux it keeps each turn's local `sprite exec` with `/proc` and a subreaper; on macOS with each turn's process group, `ps` and `lsof`). Runs are saved in `$OPENWIZ_SPRITES_STATE` (default `~/.local/state/openwiz-sprites`), owner-only. The harness's key stays in a Fly [connector](https://docs.fly.io/sprites/concepts/connectors), and the Sprites gateway attaches it to each request, so neither the driver nor the Sprite ever holds it.

Each `sprite` command and flag below is in Fly's [CLI reference](https://docs.fly.io/sprites/cli/commands). Every one carries `-o <org>`, the organization in `$OPENWIZ_SPRITES_ORG` when the run started, which the run saves: a later `sprite org set-default`, a `.sprite` file or a changed variable never moves a run to another organization ([switching organizations](https://docs.fly.io/sprites/cli/authentication#switching-organizations)).

| Command | What it does on Sprites |
| --- | --- |
| `start` | Checks the harness, the effort, `$OPENWIZ_SPRITES_ORG` and the two connections the start needs first: its harness's model connector (Anthropic for `claude`, OpenAI for `codex`) and GitHub's. It refuses before it creates anything. Then `sprite create -o <org> --skip-console --label openwiz openwiz-<run>`: a new Sprite for the run, with the `openwiz` label that your connectors' access policies match (below). It reads the new Sprite back once with `sprite api -o <org> /sprites/<name>` (Fly's [Get a sprite](https://docs.fly.io/sprites/api/sprites/get-a-sprite)), which must name that organization, and saves the Sprite's `id`, so that `stop` destroys only that Sprite and can later confirm it is gone. One `sprite exec -o <org> -s <name> --stdin -- sh -s` gets an install script on its standard input. The script installs the WizSkills release OpenWiz pins (`wizskills.lock`), the way the boat driver installs the pinned release, and the harness. It installs `openwiz-push` (below) in `~/.openwiz/bin`. It writes `~/.openwiz/env`, which holds the gateway URLs and the placeholder key word. So no connection id is ever on a local command line. Then the first turn: a local `sprite exec -o <org> -s <name> --no-stdin -- <turn>` under the driver's own supervisor. The turn reads `~/.openwiz/env` and must print that it began before the driver answers. For `claude` the command is `claude -p --session-id <uuid>`, with `ANTHROPIC_BASE_URL` set to the Anthropic connector's gateway URL, `https://api.sprites.dev/v1/gateway/anthropic/<$OPENWIZ_SPRITES_ANTHROPIC>`. For `codex` it is `codex exec --json`, with `OPENAI_BASE_URL` set to the OpenAI connector's, `https://api.sprites.dev/v1/gateway/openai/<$OPENWIZ_SPRITES_OPENAI>/v1`; the thread id it prints is saved. The agent's GitHub calls go to `OPENWIZ_GITHUB_API`, `https://api.sprites.dev/v1/gateway/github/<$OPENWIZ_SPRITES_GITHUB>`. Fly's [gateway URL](https://docs.fly.io/sprites/concepts/connectors#calling-a-connector-from-a-sprite) names the provider and the connection id as separate parts. The gateway URLs are the only connector values the driver passes. The key variable the harness insists on, `ANTHROPIC_API_KEY` for `claude` or `CODEX_API_KEY` for `codex`, holds the fixed word `openwiz-sprites-gateway-holds-the-key`. That word is not a key, and the kit's credential check does not take it for one. If any step after the create fails, `start` destroys the new Sprite before it refuses. |
| `wake` | Refused after a driver `stop`, and for an unknown run (driver v1, D5). While the last turn still runs, nothing: that agent is awake and reads the ticket itself. Otherwise a new local `sprite exec` turn with `claude -p --resume <uuid>` or `codex exec resume <id>`: the same agent, with its memory. A paused Sprite wakes on the `exec`, and its disk (with `~/.claude` and `~/.codex`) survives the pause. |
| `stop` | Ends every local process the turns started. Then it reads the Sprite with `sprite api -o <org> /sprites/<name>`, and only when that names the saved `id` does it run `sprite destroy -o <org> --force <name>`: the Sprite and its disk are gone for good. A Sprite of that name with another `id` is not the run's, and is never destroyed: the run's own is already gone. A read that can't say, or that names another organization, destroys nothing. It confirms on that one Sprite, never with `sprite list` (a list comes in pages and can leave a Sprite out). The same read must answer Fly's documented 404, `Sprite not found`, and a 404 counts only for a run whose start saved that Sprite's `id`. The driver retries once. If it can't confirm, `stop` says so and names `sprite info -o <org> <name>` to check by hand. Stopping a run that is already stopped answers again (driver v1, D6). |

**Pausing.** A Sprite is active, and billed for compute, while something uses it, and an `exec` command still running counts. About 30 seconds after the last activity it pauses: compute billing stops, and the disk stays ([lifecycle](https://docs.fly.io/sprites/concepts/lifecycle), [idle detection](https://docs.fly.io/sprites/working-with-sprites#idle-detection)). So a running turn, an open `sprite exec`, keeps its Sprite active, and between turns the Sprite pauses on its own. Each turn runs under the driver's own supervisor, so the driver answers at once and `stop` reaches every process the turn started. Locking, saving a run before starting anything for it, and the supervisor follow the [boat driver](../boat/README.md): a wake and a stop take turns, and no run is left with two agents or with one left running.

**No key in, no diagnostic out.** The driver never reads, passes or prints a key (driver v1, N1 to N3). It calls `sprite` with your environment unchanged and sends no GitHub login into the Sprite. The connection ids it reads are not secrets: a connection id only names a connector, and the gateway accepts a call only from a running Sprite that the connector's access policy lets in. A failed `sprite` command answers fixed words that name the failure and its fix; `sprite`'s own text never reaches the driver's answer.

`version` adds `many-at-once` and `own-sandbox` to `can`: every run gets its own Sprite.

## Before the first run (yours to do)

1. Install the [`sprite` CLI](https://docs.fly.io/sprites/cli/installation) (`curl -fsSL https://sprites.dev/install.sh | sh`) and sign in to it yourself: [`sprite login`](https://docs.fly.io/sprites/cli/authentication) signs you in to your Fly.io account in the browser. Use `sprite login -o <org>` to pick the organization the Sprites run in, and set `$OPENWIZ_SPRITES_ORG` to its name, as `sprite org list` shows it. `start` refuses without it.
2. **Add the connectors,** in the Fly.io dashboard: your organization, then Sprites → Connectors → Add connector ([connectors](https://docs.fly.io/sprites/concepts/connectors), [catalog](https://fly.io/sprites/ecosystem/)). You add the key there, and it never leaves the connector:
   - for `claude`: the **Anthropic** connector, with an API key from the Anthropic Console;
   - for `codex`: the **OpenAI** connector, with a project API key from platform.openai.com (this driver doesn't use the Codex connector yet);
   - and the **GitHub** connector, which you authorize through GitHub's own consent screen, for the agent's access to your repositories, issues and pull requests.
3. **Give each connector an access policy** on its detail page (Access Configuration): turn off "Allow all sprites" and set **Sprite Labels** to `openwiz`, the label `start` puts on every Sprite it creates. A connector is deny-by-default: with no policy it refuses every Sprite, and the run's model calls fail with `403 forbidden`. Don't use "Allow all sprites": it lets every Sprite in your organization use the key.
4. **Name the connections,** not the keys: set `$OPENWIZ_SPRITES_ANTHROPIC` (for `claude`) to the Anthropic connector's connection id, or `$OPENWIZ_SPRITES_OPENAI` (for `codex`) to the OpenAI connector's, and set `$OPENWIZ_SPRITES_GITHUB` to the GitHub connector's. Each one is shown on its connector's detail page with its gateway URL, and `start` refuses without the two it needs. The id is not a secret. The key stays in the connector, the gateway attaches it on each request, and the Sprite and the driver never see it.

**Taking the key back.** Deleting a connector stops every future gateway call through it at once; Fly destroys its stored credential ([connector deletion](https://docs.fly.io/sprites/concepts/connectors#list-inspect-delete)). It doesn't stop a Sprite or a turn that is already running. To cut off access, also `stop` every run that uses it (or `sprite destroy` its Sprite), and revoke or rotate the key where it was issued: in the Anthropic Console for the Anthropic connector, in your OpenAI project for the OpenAI connector, and in your GitHub settings for the GitHub connector's authorization.

`harness` is `claude` or `codex`, the two with a connector above; `start` refuses any other harness before it creates anything.

**Costs:** Sprites bills compute by the second while a Sprite is active, and nothing for compute while it is paused, plus the storage it writes, to your Fly.io organization ([Sprites](https://docs.fly.io/sprites)). `stop` destroys the Sprite, which ends both. The provider bills the model: your Anthropic account for `claude`, your OpenAI project for `codex`.

**Effort:** a `start` may name an effort, and the driver passes it by the harness's documented flag: `claude --effort <effort>` ([Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference)) or `codex exec -c model_reasoning_effort=<effort>` ([Codex config reference](https://developers.openai.com/codex/config-reference)). `version` lists `effort` in `can`. An effort the harness can't take (for `claude`, anything but low, medium, high, xhigh or max; for `codex`, anything but those or ultra; for any other harness, every effort) is refused, and the refusal creates nothing. Its `next` is: `this host can't set effort: remove the effort for this harness in your Models table or Roster to run it at the host's default`. An effort is never dropped or swapped for a nearby one. With no effort, the harness runs at its default. The prompt tells the agent to write its status note's model as `<model> <effort> effort` or `<model> default effort`.

**Publishing the branch: `openwiz-push`.** A Sprite has no GitHub login, and Fly documents the gateway for REST calls, not for `git push`. So the prompt tells the agent to publish with `openwiz-push <branch>`, never `git push`. It also tells the agent to make every GitHub API call to `$OPENWIZ_GITHUB_API` with no `Authorization` header, because the gateway adds the login. `openwiz-push` is a small standard-library helper that `start` installs in the Sprite. It sends the branch's new commits with GitHub's Git Database API: blobs, trees and commits, then it creates or fast-forwards the branch's ref. It never handles a token. Its limits:
- **Fast-forward only.** It refuses anything else before it writes anything.
- **Commits in UTC and unsigned**, so that GitHub writes each commit with the same sha. It checks each sha GitHub answers, moves the ref last, and confirms the ref it gets back.
- **No re-uploads.** It skips every blob that a commit GitHub already holds reaches: the branch's head there and every commit under the new ones, with all their history.
- **At most 200 changed files** per push. A bigger push is refused in one line before any write.

**Public repositories only.** The prompt has the agent clone with an anonymous `git clone https://github.com/<owner>/<name>.git`, which has no login. So a private repository can't be checked out this way, even when its GitHub connector can read it, and needs another checkout path that this driver doesn't ship.

A typical push of 10 changed files makes 15 REST calls as a new branch and 14 as a fast-forward, measured on the fixtures' synthetic gateway.

**Not yet checked live:** that the GitHub gateway takes the Git Database paths and writes each commit with the same sha, that Claude Code and Codex answer through the gateway with the placeholder word, and that `sprite api -o <org> /sprites/<name>` reaches `GET /v1/sprites/<name>` in that organization. The live check (#2642) answers each and records how the branch was pushed.

## The kit

```sh
python3 -I kernel/driver-kit/kit.py --driver adapters/sprites/driver \
  --repo <owner>/<throwaway> --ticket <n> --harness claude --model <model>
python3 -I adapters/sprites/test_driver.py      # the fixture tests, on a synthetic sprite CLI
```

The kit run creates a real Sprite in your organization and calls the model through your connector, which both cost money; `sprite destroy -o <org> --force <name>` any Sprite it leaves. `fixtures/bin/sprite` is a synthetic `sprite` CLI, whose `exec` runs a synthetic harness locally.
