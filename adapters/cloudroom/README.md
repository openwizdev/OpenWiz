# Cloudroom driver

Login: held by Cloudroom

Effort: passed as `--reasoning-level <effort>` to `room-cli thread spawn`, for each level `room-cli provider models <provider> --json` lists for the start's harness and model. Any other harness, model or level is refused with driver v1's refusal text before anything is saved or started; a start without an effort runs at Cloudroom's default.

| Harness | Effort (as `room-cli` 0.1.120 lists it) |
| --- | --- |
| `claude` (Cloudroom's `claude-code`), `codex`, `cursor`, `opencode` | `--reasoning-level <effort>`, for the levels Cloudroom lists for the model (such as `low`, `medium`, `high`, `xhigh`, `max`) |
| `pi`, `hermes`, `droid`, `kimi`, `antigravity`, `fx`, `openclaw`, `agent-zero`, and every other provider Cloudroom lists no models for | can't (Cloudroom lists no models, and so no levels, for it) |

A [driver v1](../../kernel/driver.v1.md) for [Cloudroom](https://cloudroom.dev): each run is one Cloudroom thread. One Python file, standard library only. **Platforms:** Linux and macOS, Python 3.9 or later (the turns run in Cloudroom's own sandboxes; the driver only calls `room-cli`). Run it inside a Cloudroom thread of the project the repository belongs to, where `room-cli` is already signed in and `ROOM_PROJECT_ID` is set; the threads it starts are that thread's children, each in its own sandbox.

| Command | What it runs |
| --- | --- |
| `start` | `room-cli thread spawn --parent-self --project $ROOM_PROJECT_ID --provider <harness> --model <model> [--reasoning-level <effort>] --title "#<ticket>: <repository> builder (<run>)" --prompt <the skill's one-line brief> --json`. The harness `claude` is Cloudroom's `claude-code`; other names pass as they are. A start with `effort` first reads `room-cli provider models <provider> --json` and passes `--reasoning-level` only when the start's model lists that level; otherwise it refuses with driver v1's refusal text, before the run is saved. The run is saved as `starting` first (no folder to keep it, nothing starts), and finishes starting only once Cloudroom's answer names a thread of this project and that is saved. If Cloudroom may have made a thread the driver could not save, the answer says the outcome is unknown, never retry |
| `wake` | `room-cli thread tell <thread> --mode queue --message-file <file>`: "You were woken for `<repository>#<ticket>`: read the ticket again, edit your own status note, and carry on". It answers `woke` only when `room-cli` accepts the message; a refusal is an error that leaves the run for the next wake. A run that is stopped, or never finished starting, takes no wake |
| `stop` | Marks the run stopped, then `room-cli thread archive <thread>`, which stops the thread and archives it. A run whose thread id was never saved finds its thread by its title (`room-cli thread list --json --project <project>`, or `room-cli thread list --json` where the Cloud `room-cli` refuses `--project`, only from the thread that started the run). It archives a thread only when exactly one row in the list has the run's title and that row's project and parent are strings equal to the run's saved ones (a Local row's `projectId` and `parentThreadId`; a Cloud row has `parent` and no project, so on Cloud this lookup always refuses). A list it cannot read, a second titled row, or a titled row whose project or parent is missing, malformed or conflicting, is an unknown outcome that archives nothing and leaves the run for the next `stop`. A refused archive leaves the run stopping: no wake, and the next `stop` archives again. Before anything else, `stop` writes `stop` over the `live` in the run's lock file, which exists from `start`, and sets that file's modification time to the epoch, which its owner can do even when neither the file nor its folder takes a write. `wake` goes on only when the lock file reads exactly `live`: either mark, an empty file (a stop killed after it made a lost lock file again and before it wrote its mark), any other text, or an unreadable or missing lock file is refused for good; only `stop` makes a lost lock file again. A `stop` whose run record is lost (its state folder went away) looks for the run's thread among the calling thread's own children, by the same list and the same rules, matching a title that ends with ` (<run>)`. A Cloud row names no project, so for its one match the driver reads `room-cli thread show <thread> --json`, after the same credential check, and takes the thread's `projectId` and `parentThreadId` from it. It archives exactly one such thread, in the caller's project under the caller's thread, and otherwise archives nothing and says so. It saves the run as stopped before the archive, so a retried `stop` answers stopped. A `wake` on such a run is refused |

Runs (run id, thread id, request) are kept privately in `$OPENWIZ_CLOUDROOM_STATE` (default `~/.local/state/openwiz-cloudroom`, owner-only). A run id never shows its thread. A wake or a stop holds the run's lock (`<run>.lock`) throughout, so they take turns. Each turn runs inside the Cloudroom thread, so archiving the thread ends everything the run started there; the kit sees only the local `room-cli` calls.

**Local and Cloud.** Every `room-cli` answer the driver reads is asked for with `--json`: a Local `room-cli` on your own machine prints a table without it and lists threads as a bare list, and the Cloud one lists them as `{"children": [...]}`. The driver reads both. `wake` and `archive` read only `room-cli`'s exit code.

**Logins.** The driver never reads, adds or passes a login: `room-cli` runs with the caller's environment unchanged, and inputs carry no credential (D1, N1 to N3).

**No credential in, no diagnostic out.** `start` refuses a field whose value has a credential's shape, by the driver kit's own check (`kernel/driver-kit/kit.py`), before it saves or starts anything; its error names the field, never the value, and without the kit it refuses every start. A spawn receipt whose thread id has a credential's shape is never saved or passed on: the run stays `starting`, and `stop` finds its thread by title. `start` loads the check once, before it saves anything, so a kit that goes missing during the spawn cannot turn a started thread into a run marked as never started. `stop` passes a thread id it found by title only after the same check, and without the kit, or for an id with a credential's shape, it archives nothing and names the run's title for archiving by hand. A failed `room-cli` command answers fixed words: a sign-in failure, named only by an explicit sign-in phrase (such as "not signed in", "signed out" or "log in"), as one; any other nonblank output, on stdout (a structured error's text, or plain text) or stderr, as an error the driver does not repeat; and silence as no answer. `room-cli`'s own text never reaches the driver's answer.

## Waking on GitHub's events

GitHub's events reach a fleet through launch-fleet's route (#1329's FF2): the repository's webhook runs the project's wake loop, its tick runs `fleet.sh wake` on the numbers the events name, and for a spec with a fleet loop that runs the loop. The fleet wake then delivers to the ticket's builder with `room-cli thread tell <id> --mode queue --message-file <file>`, counting it only on `tell`'s own acceptance. `wake` is exactly that delivery, so a fleet that keeps a run id calls `driver wake` there instead, with the same rules.

## Tests and the kit

```sh
python3 -I adapters/cloudroom/test_driver.py   # the kit's five checks and the wake route, on a synthetic room-cli
python3 -I kernel/driver-kit/kit.py --driver adapters/cloudroom/driver \
  --repo <owner>/<throwaway> --ticket <n> --harness claude --model claude-opus-5-5   # the real host
```

`fixtures/room-cli` is a synthetic `room-cli`: it never reaches Cloudroom, and runs each thread's turns as local processes of the kit's fake harness. The kit sees only processes on its own machine, so on the real host its stop and token checks see `room-cli` itself, not the remote thread; that thread ends when Cloudroom archives it.
