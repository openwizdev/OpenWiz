# boat.dev driver

Login: held by boat.dev

A [driver v1](../../kernel/driver.v1.md) that runs each builder in its own [boat.dev](https://boat.dev) cloud sandbox, through your own signed-in `boat` CLI. One Python file, standard library only. **Platforms:** Linux and macOS, Python 3.9 or later (on Linux it keeps each turn's processes with `/proc` and a subreaper; on macOS with each turn's process group, `ps` and `lsof`). Runs are saved in `$OPENWIZ_BOAT_STATE` (default `~/.local/state/openwiz-boat`), owner-only.

| Command | What it does on boat.dev |
| --- | --- |
| `start` | `boat new --name openwiz-<run>`. Then one `boat exec` installs the WizSkills release OpenWiz pins (`wizskills.lock`) in the sandbox. It fetches only that tag, once, into a local repository, and checks its commit and tree against the lock. It takes that commit's own `install.sh` by its full sha and runs it with the release URL pointed at the local repository, so nothing more is fetched. It checks that the installed release is exactly the pinned commit and tree, and links each skill into `~/.claude/skills/` and `~/.agents/skills/` without replacing any existing entry. A second `boat exec` makes one `git push --dry-run` of a new branch, `openwiz-push-check-<run>`, to `https://github.com/<repository>.git` from an empty local repository. If it fails, `start` refuses with one line naming the repository and the fix (give the GitHub account connected in boat's dashboard write access to it), and no turn starts. The check covers less than a real push: a dry run sends no update, so GitHub answers only whether the sandbox's git login, the GitHub account connected in boat's dashboard, may push to the repository at all, and the builder's `git push` uses that same account. It can't see branch rules. A ruleset that restricts creating or updating the builder's branch, and doesn't let that account push there, still refuses the builder's push at the end of its turn. Let that account through the ruleset (its bypass list), or exclude the builder's branches. Then `boat prompt <sandbox> --new --provider <harness> --model <model>` with the ticket and skill. Once boat has queued the agent's turn, it watches that first turn for `$OPENWIZ_BOAT_SETTLE` seconds (default 20, at most 60; `start` refuses any other value before it creates a sandbox) before it answers. A first turn that logs a `usage_limit` event (an expired login or a rate limit), or that ends with no tool call, fails `start`: the answer names the limit type (`auth_expiry` or `rate_limit`, anything else as `unknown`) and the turn log's path, never the log's text. If the install, the push check, the prompt or the first turn fails, it stops the new sandbox before refusing. |
| `wake` | While the last turn's `boat prompt` still runs, nothing: that agent is awake and reads the ticket itself. Otherwise, only while `boat info` shows the sandbox `running`, `idle` or `ready` (the states that take a prompt once a turn has ended), `boat prompt <sandbox> --resume <conversation>`: the same agent, with its memory, edits its own status note. A stopped sandbox is never resumed: after a stop, or after boat's auto-stop (an hour without a running prompt), the run stays stopped and needs a new `start`. |
| `stop` | Ends every local process the turns started (on macOS, every one it can find: see the gap below), `boat interrupt`s the agent and `boat stop`s the sandbox. The disk stays for at least 14 days at no compute cost; `boat delete <sandbox>` removes it for good. |

Each turn is a local `boat prompt` under its own supervisor, so the driver can answer at once. On Linux the supervisor is a subreaper, and `stop` reaches every process the turn started, whatever its session or environment; on macOS, every process it can find, within the gap below. The turn's output goes to an owner-only log beside the run's state, deleted on `stop`. On macOS, where there is no subreaper, a process that leaves the turn's session and is orphaned between two looks is still found by that log: every process the turn starts inherits it, and the supervisor and `stop` also take each process that `lsof -- <log>` lists holding it open for writing (the supervisor looks once more right before it exits). No process environment is read. The gap: on macOS, a process that leaves the turn's group, closes or redirects its output (as a daemon does) and is orphaned within one look escapes `stop`.

**Never two agents, and no turn left running beyond the macOS gap.** A wake and a stop hold the run's lock throughout, so they take turns. The driver saves a run before it starts anything for it. A run stays `starting` until its first turn is saved: a wake refuses it, and a stop still reaches its sandbox. If a save fails after a turn began, the driver ends that turn (and, for a start, stops the sandbox) and says the outcome is unknown, never to do it again. A stop that can't save still ends everything, then says so. It first marks the run as stopping on the run's existing lock file, both by its content and by its mtime, which its owner can set even when the file can't be written. Neither needs a new file in the folder. Until a stop succeeds, a wake refuses a run with either mark, or with no lock file, even once the folder can be written again. When no mark can be written at all (a read-only filesystem), the wake still refuses, because boat shows the sandbox stopped. Every stop of a sandbox runs `boat stop`, whatever local signalling, `boat info` or the state save did, and each failure is reported. If boat can't confirm the sandbox stopped, the answer says so and names the `boat stop` command to run. After an error the driver didn't expect, a start ends its turn and stops the sandbox, and a wake ends its new turn and interrupts its conversation, before the driver answers with the error.

**No credential in, no diagnostic out.** `start` refuses a field whose value has a credential's shape, by the driver kit's own check (`kernel/driver-kit/kit.py`), before it saves or starts anything; its error names the field, never the value. A failed boat command answers fixed words: a known error code by name (such as `provider_not_configured`), whether a structured error or only stderr carries it, a sign-in failure as one (from stderr too when the structured error names none), and anything else as an error the driver does not repeat. boat's own text, from a structured error or its stderr, never reaches the driver's answer; a failed prompt points to the run's owner-only log, which holds it.

`version` adds `many-at-once` and `own-sandbox` to `can`: every run gets its own sandbox, and a boat plan runs many at once.

## Before the first run (yours to do)

The driver never touches a login (driver v1, N1 to N3): it calls `boat` with your environment unchanged, and passes no key, token or password anywhere.

1. Install the `boat` CLI (`curl -fsSL https://boat.dev/install | sh`) and sign in to it yourself.
2. In boat's dashboard, connect GitHub (so the agent's `gh` and `git push` work in the sandbox, as your agents' account), with write access, for that connected account, to each repository you build (`start` checks it), and a way through any ruleset that restricts creating branches there (`start` can't check that) and the key or subscription for each harness you use (Agents & Proxying).
3. `harness` is one of boat's providers: `claude`, `codex`, `pi`, `opencode`, `prime`, `kimi` or `mistral`. `model` is passed to `--model` unchanged.

**Effort:** runs use the host's default effort. Driver v1's `start` has no effort field, so whatever effort a fleet configures isn't applied, and each prompt tells the agent to write its status note's model as `<model> default effort`. Passing an effort needs a driver v2 field, a separate decision.

boat bills per second while a sandbox runs, against your plan.

## The kit

```sh
python3 -I kernel/driver-kit/kit.py --driver adapters/boat/driver \
  --repo <owner>/<throwaway> --ticket <n> --harness claude --model <model>
python3 -I adapters/boat/test_driver.py      # the fixture tests, on a synthetic boat CLI
```

`fixtures/bin/boat` is a synthetic `boat` CLI. Its JSON Lines follow boat's CLI reference and the owner's live kit run (boat CLI 1.0.103): `boat prompt --json` nests the conversation id under `data` (`{"data": {"conversationId": ...}, "event": "queued"}`), and `boat info --json` nests the sandbox's fields, `state` among them, under a top-level `sandbox` key (`{"sandbox": {"id": ..., "state": "running"}}`), as live boat answered twice. With `FAKE_BOAT_INFO=flat` it prints the older flat answer, a top-level `state` (`{"id": ..., "state": "running"}`), which the driver still reads. The live runs are in `evidence/live-*.txt`.
