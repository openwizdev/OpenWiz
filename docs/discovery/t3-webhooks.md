# How GitHub events reach a T3 home

This review pins [T3 Code v0.1.13](https://github.com/pingdotgg/t3code/releases/tag/v0.1.13) (`bc0f04da94f64b5e487c598761a43b4cf06b2ac9`). The server and T3 Connect relay below come from the same tag. This is a source review for [GE1](https://github.com/openwizdev/OpenWiz/issues/3739), with live checks left to [GE8](https://github.com/openwizdev/OpenWiz/issues/3751).

## URL and reachability

- A webhook task has the local path `/api/hooks/<hook-id>/<url-token>`. The UI can join it to the environment address. Loopback is local only. A server with an independently reachable HTTPS origin can receive a direct call. GitHub cannot reach a home that is only on loopback or a private network. [Server endpoint](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L394-L408) · [Address selection](https://github.com/pingdotgg/t3code/blob/v0.1.13/packages/client-runtime/src/webhookAddress.ts#L12-L37)
- With a configured T3 Connect link, the task can return `https://<relay-origin>/v1/hooks/<endpoint-key>/<hook-id>/<url-token>`. The relay resolves the environment and forwards to its tunnel's `/api/hooks/…` path. On an unavailable home, the relay can hold the delivery if enabled for that environment. A hold can return `202` before the home receives anything. [Server Connect configuration](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/server.ts#L614-L634) · [Relay URL](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L123-L135) · [Tunnel forwarding](https://github.com/pingdotgg/t3code/blob/v0.1.13/infra/relay/src/hooks/upstream.ts#L78-L103) · [Offline handling](https://github.com/pingdotgg/t3code/blob/v0.1.13/infra/relay/src/hooks/HookForwarder.ts#L329-L386)

## Authentication and headers

- The home checks the secret URL token with a timing-safe comparison. An optional task signature check runs at the home before dispatch and computes HMAC-SHA256 on the original request bytes. GitHub's settings match native verification with header `X-Hub-Signature-256`, hex encoding and prefix `sha256=`. An invalid or missing signature on a task configured this way returns `401`. Treat the URL as a credential. [Token generation](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L635-L638) · [Token comparison](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L2198-L2223) · [Signature gate](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L2327-L2342) · [HMAC implementation](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/webhookVerification.ts#L24-L47) · [HTTP response](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/webhookRoute.ts#L169-L181)
- Connect forwards ordinary GitHub headers, including `X-Hub-Signature-256` and `X-GitHub-Delivery`, with the body. The relay signs its own delivery metadata for the home. GitHub's delivery ID is separate from the relay delivery ID. A task prompt can select `{{headers.x-github-delivery}}`; the whole-request and whole-header placeholders redact signature headers, while named placeholders return their values before rendering. Keep the signature out of the prompt. ## Payload and size

- Both Connect and the home cap the HTTP body at 1 MiB (1,048,576 bytes) and return `413` above the cap. The home decodes the request as text and fills the task's prompt from placeholders such as `{{body}}`, `{{body.action}}` and named headers. Substitution frames values as untrusted text and inserts word joiners after matched mention syntax. The task gets that prompt with empty attachments. This dispatch path exposes no original request file or webhook environment value to the run. [Relay cap](https://github.com/pingdotgg/t3code/blob/v0.1.13/infra/relay/src/hooks/HookForwarder.ts#L30-L34) · [Relay refusal](https://github.com/pingdotgg/t3code/blob/v0.1.13/infra/relay/src/hooks/HookForwarder.ts#L282-L315) · [Home cap](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/webhookRoute.ts#L63-L84) · [Home request conversion](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/webhookRoute.ts#L142-L154) · [Placeholder rendering](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/webhookTemplate.ts#L125-L175) · [Task dispatch](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L1084-L1106) · [Fresh-thread dispatch](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L1124-L1145)
- The trimmed prompt limit is 120,000 JavaScript string units, including template and framing. A prompt over that limit can return HTTP `202` with a `prompt_too_long` outcome and no run. The delivery log keeps only the first 64 KiB of a larger body and redacts signature headers. The log cannot serve as the router's byte-exact input. ## Rate limits and concurrent runs

- Connect allows 60 requests per URL and 600 per endpoint per 60 seconds. Above either limit it returns `429` with `Retry-After: 60`. The home has a separate sliding window of 60 work-starting deliveries per task per minute and a separate rejection budget. [Relay budgets](https://github.com/pingdotgg/t3code/blob/v0.1.13/infra/relay/src/hooks/HookForwarder.ts#L30-L34) · [Relay refusal](https://github.com/pingdotgg/t3code/blob/v0.1.13/infra/relay/src/hooks/HookForwarder.ts#L270-L280) · [Home limits](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L107-L109) · [Home window](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L2005-L2034) · [Rejection budget](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L2308-L2320)
- A second accepted delivery can wait behind the current dispatch. The home counts pending, dispatching and running work, plus immediate reservations, against a cap of 20 per task. A full queue returns `429` with `queue_full`. The immediate dispatch runs in the background under a per-task permit, and the task can report `succeeded` once the prompt is dispatched. A provider turn may still be active. Bound tasks queue their messages in that thread, and distinct new threads can have overlapping provider turns. ## Thread routing

- The scheduler uses the same dispatch for webhook and other task triggers. The [T3 runner rule](https://github.com/openwizdev/OpenWiz/issues/3504) for `thread: new` corresponds to `new_thread` with no bound ID. It opens a fresh thread for every dispatch and leaves the task unbound. For `thread: same`, bind the chosen thread with `continue` and send in `queue` mode. Binding alone does not force a new provider session. T3 has a separate `fresh_session` mode that queues on the bound thread with fresh provider context. [Thread modes](https://github.com/pingdotgg/t3code/blob/v0.1.13/packages/contracts/src/scheduledTask.ts#L227-L239) · [Task binding](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L1498-L1510) · [Dispatch](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L1084-L1159) · [Webhook calls the same scheduler](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L2089-L2100)

## Decision and owner settings

Choose launch-fleet's **local heartbeat with polling only** for #3716. T3's native HMAC check protects its ingress. The [GE2 contract ticket](https://github.com/openwizdev/OpenWiz/issues/3740) requires the router to verify the delivery signature when the route supplies headers and the secret is set. At this tag the router would receive prompt text, with no byte-exact body or authenticated delivery handoff to the check script. A synthetic `issue_comment` containing an `@` mention produced a different HMAC after T3 rendered its body. Routing via the rendered prompt would require changing that verification boundary. [Original bytes checked at ingress](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/webhookVerification.ts#L24-L45) · [Prompt transformation](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/webhookTemplate.ts#L149-L175) · [Dispatch input](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L1084-L1106)

| Payload URL | None. Leave the repository webhook unconfigured. |

The opt-in local heartbeat checks the GitHub records for the spec every ten minutes. Checks, merges and reviews become visible on a healthy poll, so the under-one-minute webhook target and redelivery proof do not apply. Keep the spec's 30-minute safety net. GE4 should use the polling choice in its ticket without adding a webhook trigger.
