# Shirudo as an opt-in guard on Linux agent boxes

Read on 2026-11-28 for [OpenWiz #3706](https://github.com/openwizdev/OpenWiz/issues/3706). The [research spec](https://github.com/openwizdev/OpenWiz/issues/3703) admits only permissively licensed code for adoption, and no third-party tool may become a default. This note asks whether Shirudo could guard a Linux box that runs coding agents, as something an owner turns on.

## Source read

The public repository is [`shirudo-dev/shirudo`](https://github.com/shirudo-dev/shirudo). This note reads commit [`dbdb125edbdf2cc83344669cd50f8c07d723668a`](https://github.com/shirudo-dev/shirudo/commit/dbdb125edbdf2cc83344669cd50f8c07d723668a) of 2026-11-27 on `main`, with its documentation under `Documentation/` at the same commit. The project has no release tag; its `VERSION` file reads `0.0.0-dev`, and the only GitHub release is a test-kernel pre-release. [VERSION at the pin](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/VERSION) · [Releases](https://github.com/shirudo-dev/shirudo/releases)

The README describes Shirudo as a BPF-based security platform for Linux and links the OpenAI and Cisco (Isovalent) announcement posts. This note read the repository, not those posts; their contents are unverified here. [README at the pin](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/README.md)

## What it watches and blocks

Shirudo is not a policy engine with a rule language. After boot it restricts BPF loads to signed loaders, and everything it watches or blocks ships as a signed BPF package called a upatch, built and signed on a separate operator host and pulled by the guarded machine from an OCI registry. The FAQ contrasts this with Tetragon's runtime policy files. [README at the pin](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/README.md) · [FAQ, policy language](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/start/faq.rst#L240-L254)

| What | How, at the pin |
| --- | --- |
| Processes | The `app-sandbox` upatch labels named executables; a task that ran one, and its children, may execute only files of the policies its sandbox allows. Every refusal is `EACCES`. [app-sandbox README](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/upatches/app-sandbox/README.md) |
| Files | The same sandbox can deny creating, renaming or opening for writing any file whose last path component matches a pattern, for example `*.php`. It matches names, not contents, and a descriptor opened before the task entered the sandbox still writes. [app-sandbox README, limits](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/upatches/app-sandbox/README.md#limits) |
| Network | The sandbox allows `connect()`, `sendmsg()` and `sendto()` only to listed IPv4 or IPv6 networks and refuses raw and packet sockets. Other address families and inbound traffic pass. [app-sandbox README](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/upatches/app-sandbox/README.md#limits) |
| Observation only | The `kernel-obs` upatch records executed programs, network peers, listeners, DNS answers, privilege changes and access to credential and persistence files, and enforces nothing. [kernel-obs README](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/upatches/kernel-obs/README.md) |

A sandbox is written as a `[[upatches.policy]]` table in the package's `Beefile`, naming the executables that enter it, plus a `sandbox.toml` with `exec`, `network` and `deny` keys; `gen_policy.py` compiles that file into the upatch at build time, and the operator signs the result. The package ships sandboxes for Apache httpd and PHP-FPM, not for any coding agent. The project's audience page names LLM agents as a use: limit which programs they run, which files they write and which hosts they reach. [app-sandbox README, define a sandbox](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/upatches/app-sandbox/README.md#define-a-sandbox) · [Who is shirudo for](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/start/who-is-shirudo-for.rst#L88-L103)

A sandbox is entered at the next `execve()` of a labelled file, so the agent would need restarting after the first load; a file replaced by an upgrade loses its label until the upatch loads again; and root outside the sandbox can start a task from an unlabelled file. A working sandbox for Claude Code, Codex or another agent CLI, and its effect on their tool calls, is unverified. [app-sandbox README, what a load does and limits](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/upatches/app-sandbox/README.md#what-a-load-does)

## As an opt-in guard

Shirudo cannot be added to an ordinary Linux agent box as a package an owner switches on. At the pin, a guarded machine needs all of these, with no fallback, as the [system requirements](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/operate/plan/system-requirements.rst) list them:

- A bpf-next kernel with the signed-loader interface plus the kernel patches the project carries; a release number does not identify a suitable kernel, and the test kernel reports `7.4.0-rc1-bpf-next+`. No stock distribution kernel is named as suitable. [System requirements, target kernel](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/operate/plan/system-requirements.rst#L39-L52)
- A TPM 2.0 through `/dev/tpmrm0`; there is no mode without one. In a cloud VM it needs a virtual TPM and a signed unified kernel image under UEFI Secure Boot. [System requirements, TPM](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/operate/plan/system-requirements.rst#L279-L312) · [FAQ, TPM and cloud VMs](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/start/faq.rst#L49-L68)
- A unified kernel image booted through `systemd-stub`, a dracut systemd initrd, systemd 256 or newer, two keyring kernel parameters, and root for `shirudo init`, which starts enforcement from the initrd at boot. [System requirements, target userspace](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/operate/plan/system-requirements.rst#L314-L355)
- A separate operator host with the ML-DSA-87 signing key, clang and LLVM 23, and an OCI registry to publish signed packages to. [System requirements, operator host](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/operate/plan/system-requirements.rst#L438-L470)

Once enforcing, only signed upatches run BPF on the machine, so bcc, bpftrace and other BPF-based tools stay off it. The project itself says it has no release and no format with a compatibility promise. The FAQ plans a mode for older kernels, without a TPM, for machines where root is trusted, before the first release; its timing is unverified. [Who is shirudo for, not a fit yet](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/start/who-is-shirudo-for.rst#L116-L130) · [FAQ, kernel](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/start/faq.rst#L39-L47)

What the OpenWiz specs named in [the ticket](https://github.com/openwizdev/OpenWiz/issues/3706) would gain:

- **Privacy and security, [#3456](https://github.com/openwizdev/OpenWiz/issues/3456).** That spec's telemetry guarantee is proved by a static, offline egress audit of OpenWiz's own shipped code, and it puts network monitoring at runtime out of scope. A per-process network sandbox would be a runtime layer on the owner's box rather than evidence for that audit, so it adds nothing the spec's proof table asks for. [Privacy and security spec, out of scope](https://github.com/openwizdev/OpenWiz/issues/3456)
- **AD6, [#3120](https://github.com/openwizdev/OpenWiz/issues/3120).** AD6 sets the OOM order and CPU quota of an agent's commands through `oom_score_adj` and cgroup readings, with no privilege. Shirudo's documented upatches restrict exec, file writes and connections; none at the pin addresses memory or CPU, so it would sit beside AD6 rather than serve it. [AD6 ticket](https://github.com/openwizdev/OpenWiz/issues/3120) · [app-sandbox README](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/upatches/app-sandbox/README.md)

Whether OpenWiz's own Linux agent boxes have a TPM 2.0 or could boot the required kernel is unverified: this note inspected no owner machine, as the ticket requires. [OpenWiz #3706](https://github.com/openwizdev/OpenWiz/issues/3706)

## What it records

On the guarded machine, Shirudo keeps an append-only eventlog of every change to its TPM register at `/var/lib/shirudo/eventlog`, mode `0600`, never rotated. Observation upatches such as `kernel-obs` keep their tables in BPF maps, which are sensitive on an agent box: executed programs, peers, DNS answers and credential-file access. [Eventlog reference](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/reference/eventlog.rst) · [kernel-obs README](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/upatches/kernel-obs/README.md)

| What leaves the machine | Default at the pin |
| --- | --- |
| The status keepalive, about a kilobyte of JSON with a TPM quote and the machine's `host.name`, sent by a timer about once a minute | Sent only when an OTLP endpoint is configured; nothing otherwise. The `map_export.otel_endpoint` setting defaults to empty. [Telemetry, what a target sends](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/operate/run/telemetry.rst#L25-L68) · [Configuration](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/reference/configuration.rst#L182-L214) |
| Snapshots of upatch maps, such as `kernel-obs` tables | Sent to the JSON file or OTLP collector the signed config names, with an optional S3 bucket for oversized snapshots; with no destination, the dump goes to the local journal. [Telemetry, what a target sends](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/operate/run/telemetry.rst#L25-L45) |
| Package pulls from OCI registries by timer | Each repository definition requires an `endpoint` the operator writes, and the repository at the pin ships no default definition. [Configuration, repository definition](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/reference/configuration.rst#L477-L500) · [systemd units at the pin](https://github.com/shirudo-dev/shirudo/tree/dbdb125edbdf2cc83344669cd50f8c07d723668a/systemd) |

So the documented default sends nothing off the machine, which meets the zero-telemetry rule. A text search of the C sources at the pin found only help-text placeholder URLs, but the binary was not built or run, so the absence of other outbound calls is unverified. [Source tree at the pin](https://github.com/shirudo-dev/shirudo/tree/dbdb125edbdf2cc83344669cd50f8c07d723668a)

## Licence and maintenance

The licence file is the BSD 2-Clause text, SPDX `BSD-2-Clause`, which requires the copyright notice, conditions and disclaimer to accompany source and binary copies. The README adds that the BPF programs are dual-licensed BSD/GPL and that vendored third-party files keep their own SPDX identifiers. The licence is on the permissive list, so it does not by itself rule out adoption. [Pinned licence](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/LICENSE) · [README, license](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/README.md#license)

The first commit on `main` is from 2026-10-18 and the pin is about 1,900 commits later, with pushes on the day of this reading. The maintainers file lists five core maintainers, three of them at Isovalent at Cisco and one at Meta; the governance file requires another maintainer's approval for each non-trivial change. No release, support window or compatibility promise exists yet. ## Reasons

- The licence allows adoption, but adopt needs a named spot in OpenWiz, and neither the privacy spec's static egress proof nor AD6's resource limits needs a kernel guard. [Research spec](https://github.com/openwizdev/OpenWiz/issues/3703) · [#3456](https://github.com/openwizdev/OpenWiz/issues/3456) · [#3120](https://github.com/openwizdev/OpenWiz/issues/3120)
- A WizMarket listing would point owners at something they cannot turn on: a guarded box needs a patched bpf-next kernel, a TPM 2.0, a measured UKI boot and a separate signing host, and enforcement then bars other BPF tools. That is a rebuild of the machine, not an opt-in. [System requirements](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/operate/plan/system-requirements.rst) · [Market spec](https://github.com/openwizdev/OpenWiz/issues/3384)
- The project is pre-release with no compatibility promise, and it ships no sandbox for a coding agent, so any listing card would describe an unproven setup. [Who is shirudo for, not a fit yet](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/start/who-is-shirudo-for.rst#L116-L130) · [app-sandbox README](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/upatches/app-sandbox/README.md)
- Worth a fresh look once a tagged release ships the planned mode for stock kernels without a TPM; this note proposes no ticket for that. [FAQ, kernel](https://github.com/shirudo-dev/shirudo/blob/dbdb125edbdf2cc83344669cd50f8c07d723668a/Documentation/start/faq.rst#L39-L47)

**Verdict** — no. Shirudo is BSD-2-Clause and sends nothing off the machine by default, but at this pin it cannot be an opt-in on an ordinary Linux agent box because it needs a patched bpf-next kernel, a TPM 2.0 and a measured boot, it has no release, and no OpenWiz spec has a spot it would fill.
