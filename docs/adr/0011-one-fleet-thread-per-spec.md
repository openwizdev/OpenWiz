# One fleet thread per spec owns its agents

A fleet is run by one long-lived fleet thread per spec, which starts every builder and reviewer of that spec itself, so it can always message, check and archive them; the loop wakes that same thread on a schedule instead of starting a fresh thread each time. GitHub stays its only memory, so a replacement thread can take over from the records, and it talks to the orchestrator only through GitHub records. Why: in the 0.0.5 acceptance a CloudRoom thread could message and archive only threads it started itself, so fresh-thread ticks couldn't route findings, ask for re-checks or archive agents an earlier tick had started. This refines ADR 0007 (the loop stays separate from the orchestrator). In 0.0.6 the routing moves into OpenWiz's own code.

Source: Jake, 2026-10-31: each spec keeps one fleet owner capable of reaching its agents across ticks ([private record](https://github.com/jparker2006/ClosedWiz/issues/1276#issuecomment-6704797460)).

**Refined by #1456 (spec #2185, OB4):** parent-only reachability no longer forces recovery through the orchestrator. One logical owner per spec is now the current admitted generation claim, shared by project and spec ticks, not the thread that started an agent. A standby outside the PC's failure domain records intents on GitHub and each recipient reads them on its own wake; nobody archives or replaces a live builder to gain access. Every effect stays disabled at OB3's boundary until its actual endpoint checks generation and operation (OB-A1), and the access itself stays Unverified until #2244's discovery and OB8's live run. Source: Jake, 2026-11-12, spec #2185 revisions 7/8 ([private record](https://github.com/jparker2006/ClosedWiz/issues/2185#issuecomment-6815747648)).
